## Phase 1 — Kernel skeleton

Target: a "hello world" agent runs, calls one LLM, checkpoints, restores, exits cleanly. ~1500 lines of TypeScript.

> **Status as of this commit:** 10 of 10 numbered items done, plus the unnumbered `driver_registry.ts` — **the whole v0 kernel of ARCHITECTURE §4 ("ten kernel modules + one driver registry") has landed.** The foundation (`types.ts` + `errors.ts`) plus `recorder.ts`, `process_table.ts`, `signals.ts`, `ipc.ts`, `memory.ts`, `checkpoint.ts`, `fork.ts`, `scheduler.ts`, `init.ts`, the capstone `syscall_dispatcher.ts` (#014), and `driver_registry.ts` (§4.11) are in. The dispatcher is the single front door: it enforces the state gate (`ESTATE`), the forkable-region rule (`EREVERSIBLE`), enter/exit/trap recording, and budget accounting + `SIGXCPU`, then routes to each module and calls `init.handleZombie` on `exit()`. The driver registry version-checks (`abiCompat` semver gate, ABI §9.7) and routes LLM / tool / memory drivers, and its `llmResolver()` / `toolResolver()` feed the dispatcher's `ResolveLLMHook` / `ResolveToolHook` — those hooks are no longer placeholders. One honest v0 deviation: `memory.ts` / `ipc.ts` / `fork.ts` / `checkpoint.ts` predate the dispatcher and still write their own records, so it gates and routes those syscalls without re-recording them (collapsing them onto the dispatcher is a documented follow-up); likewise `MemoryManager` keeps its own backing→driver map, which boot copies from the registry. **The kernel now boots.** `boot.ts` (the agent runner) assembles all ten modules + the registry into a live `Kernel`, wires the scheduler's `resume` continuation to a run-to-completion quantum, materialises the `CortexContext` proxy, and clears the ARCHITECTURE §13 acceptance bar end to end: *spawn a process that calls `llm_call` against the mock driver (#022), exits, gets reaped.* 362 smoke checks green. What remains for a usable v0 is the rest of the Phase 2 drivers (#024 openai onward — #023 deepseek, the first real LLM driver, has landed) and the Phase 3 CLI.

## Phase 3 — CLI (`cortex` / `ctx`)

The user-facing surface. Should feel like a real OS shell.

- [x] **#029** `cortex spawn` — start an agent, print PID → implemented (`--role`, `--task`, `--system`, `--module`; env-driven driver selection). Hardened this pass: `--module` spawns a user agent module; the previously-dead `--driver`/`--model`/`--max-tokens` now flow through `AgentSpec` into the prompt agent's `llm_call` and `--token-budget` becomes a real spawn budget; every spawned agent gets the three default memory regions (episodic/semantic/procedural) so `memory_write` does not trap ENOENT; and a reaped process's exit status is recovered from the `.crec` exit record instead of being hardcoded to `code 0: completed` (a failed run is no longer reported as success). **`cortex spawn --live` spawns into the running kernel** instead of booting a throwaway one: the agent is created by the daemon's kernel through the ordinary `spawn` syscall on the dispatcher (so the state gate, the capability gate and the recording path apply exactly as they do locally), it gets a real PID in the live process table, and the command that started it can exit while the agent keeps running. It is opt-in because the default `spawn` is a *runner* — one kernel per invocation, result printed, exit — and silently changing the lifetime of the most-used command is the kind of quiet semantic change this project does not make. Two things a live spawn does not carry, both printed in the command's own output: the agent's stdout belongs to the daemon, and the LLM driver (API key included) is read from the *daemon's* environment, not the shell's.

- [x] **#031** `cortex attach` / `detach` — interactive session with a running agent

It dumps every syscall the agent has made so far and, in follow mode (the default), polls the log every 250ms and prints new frames as another `cortex` invocation appends them; SIGINT / SIGTERM detach cleanly. It reuses the same `formatRecordLine` as `cortex trace`, so both commands print identical rows for the same file. The read half is unchanged — `--interactive` adds the write half, it does not replace the trace.
- [x] **#032** `cortex kill` — send signals → implemented (`--signal`; all 13 cortex signals). **Now it signals for real.** With a live kernel (`cortex daemon run`), the signal is delivered through the kernel's own signal engine: the target's disposition is honoured, the signal is queued when the target is not running yet, the outcome is reported (`delivered` / `queued` / `dropped`), and the delivery is recorded in the kernel's `.crec`. Without one, there is no process to signal, so the command marks the process terminated in the on-disk metadata and says that is what it did.
- [x] **#033** `cortex trace` — strace-style syscall log, live or from `.crec` file → implemented (reads `.crec` by PID or file path)
- [x] **#034** `cortex fork` — clone a running process at its current state → implemented (`--tag`, `--budgets`). **And it can now find the process.** The command booted a kernel of its own and looked the PID up in *that* kernel's table — which holds exactly one entry (init) — so it answered "no such process" for a process that was running somewhere else, and could not succeed in any scenario. A fork snapshots a *running* process, so there is no local fallback to fall back to: the command asks the kernel that has one (`cortex daemon run`), and says plainly what is missing when there is none. The fork is the target's own syscall (the ABI allows `fork` from RUNNING / BLOCKED / STOPPED / SUSPENDED), so the frame lands in the parent's log and the shared causal past it records is where `cortex diff` cuts the two branches apart. The child is minted by that kernel and keeps running there — which makes Demo C drivable from a shell: fork a running agent, send the two branches different instructions, diff them.
- [x] **#035** `cortex checkpoint` / `cortex restore` → implemented (`--tag`, `--detach`; restore by `--chain` or `--tag`). Cross-invocation restore now works: `bootCliKernel` injects a disk-backed `restoreContext` (rebuilds the agent spec from `<pid>.meta.json`, since the `.csnap` body deliberately omits it), seeds the PID counter from `maxPidOnDisk` so restore never reuses the suspended original's PID, and `--tag` resolves to a chain ID by scanning `.crec` checkpoint records (the tag is not in the `.csnap`). `spawn` now reports a self-checkpointed SUSPENDED process cleanly (with a `restore` hint) instead of as a timeout. **And the snapshot of a *running* process now works.** `cortex checkpoint <pid>` used to be a command that could not succeed: a checkpoint captures a live process, and the short-lived CLI kernel holds exactly one entry (init), so the PID it was asked about was never there — the answer was always "no such process". With a live kernel it takes the snapshot through the dispatcher (so the state gate and the capability gate apply exactly as they do locally) and reports the chain id and the file; `--tag` is recorded in the checkpoint frame and `--detach` suspends the process, so "save and stop" is now something the shell can do to a running agent. The other route is `SIGUSR2`, whose default action is now `checkpoint` (docs/PROCESS.md §7.4) — the only way to ask *another* process to snapshot itself, because `checkpoint` is a self-syscall and the ABI gives it no target argument. **And the restore now has a live half.** `cortex restore` used to restore into a kernel of its own, run the restored agent to completion, and exit — so the restored agent's life was bounded by the command, which is the wrong shape for the promise a checkpoint makes (*pause, and come back to work*). `cortex restore --live` asks the running kernel instead: the `.csnap` is found on disk by chain id (the checkpoint manager searches `processes/<pid>/checkpoints/`, so a snapshot taken by an earlier kernel loads too), the restored process is minted by that kernel with a new PID and its role intact, and it stays there — reachable by `send`, `checkpoint`, `kill` and `attach --interactive`. The kernel rebuilds the restored agent's spec from **the process it is still running** first and the disk second, because a running process has no `meta.json` yet (the CLI writes one when a process exits) — which is exactly the case `--live` exists for. The lookup cannot confuse two processes: a kernel seeds its PID counter past everything already on disk, so a PID from an earlier session is never handed out again, and a table hit is always the very process that took the snapshot. **And `--tag` was broken.** The tag is an argument and the chain id is a result, so since the `checkpoint` syscall moved onto the dispatcher's recording path they landed in different frames of the same call — the `enter` frame carries `{tag, detach}`, the `exit` frame carries `{chainId, byteSize, syscallLogOffset}`. The tag reader still looked for one frame carrying both, which the old checkpoint module happened to write; when the frames split, it quietly stopped finding anything, and `cortex restore --tag X` answered "no checkpoint found with tag X" for a checkpoint that was sitting on disk. The reader now pairs the two frames by call id (and still reads the old single-frame shape). The check that should have caught it wrote a hand-made frame with both facts in it, so it kept passing; the new check takes a real checkpoint through the kernel and resolves its tag back. **And a snapshot now outlives the kernel that took it.** The `.csnap` body deliberately omits the role/agent spec, so a restore has to be told what to rebuild — and until now the only thing on disk that carried it was the `meta.json`, which the CLI writes when a process *exits*. So a snapshot of an agent that was still running (a daemon's agent, say) had no spec anywhere once its kernel was gone, and could not be restored in a later session: the spec died with the kernel. The kernel now reports every birth (`KernelOptions.onProcessStart`, the counterpart of `onProcessExit`) and the CLI writes the spec down at creation, in `processes/<pid>/spec.json`. Every process is born through `table.allocate()` — the dispatcher's `spawn`, init's daemon registration, and `restore` all land there — so this one hook covers all of them, and the restore context reads it back: the process table first (a process this kernel still runs), then `spec.json`, then `meta.json`. The flagship story now works end to end: a daemon's agent checkpoints itself, the daemon is killed uncleanly, and `cortex restore --tag` brings it back in a fresh session.
- [x] **#036** `cortex send` — IPC from the shell → implemented (`--channel` or PID target). **Now it delivers.** The short-lived CLI model could not deliver anything: the fresh kernel's process table holds exactly one entry (init), so a message addressed to a real agent had no inbox to land in, and the kernel exited a millisecond later taking it with it — the syscall was recorded, nothing was delivered. With a live kernel, `cortex send <pid> <msg>` hands the message to a process that is actually running, through the same prepare/commit transaction the kernel uses internally. Without one, the command says so plainly instead of claiming a delivery it did not make.
- [x] **#037** `cortex limit` — set token / cost / time budgets per process → implemented (`--tokens`, `--usd`, `--wall-time`; show mode when no limits given)
- [x] **#038** `cortex diff` — compare two forked branches' syscall logs and outputs → implemented (`src/cli/diff_core.ts` for the pure logic + `src/cli/commands/diff.ts` for I/O). **The non-obvious part:** you cannot just diff two `.crec` files. A forked child inherits the parent's *state*, not its *log* — the shared causal past exists only in the parent's file. A naive head-to-head align therefore reports the entire shared history as "A only". So diff reads `sharedCausalPast` out of the parent's `fork` record, cuts the parent's log at that byte offset, and only then aligns the two tails with an LCS. LCS rather than a positional compare because branches can *re-converge* (both exit the same way) and a positional compare would call that a difference; LCS also reports one insertion as one insertion instead of a cascade. Signature comparison deliberately excludes `timestamp`/`durationMs`/`callId`/`byteOffset` — otherwise every line differs and the diff is useless. Falls back to a prefix compare (flagged as degenerate, out loud) above `MAX_LCS_CELLS`. Also surfaces `irreversibleInPast` (STATE.md §5.4: those actions happened once, in reality, and both branches inherit them — whoever wins, they already happened). 19 smoke checks, plus `examples/fork-compare-agent.ts` for the live demo.
- [x] **#039** `cortex daemon install` — register a long-running agent to start on boot
  - **v0 (this pass):** `cortex daemon install <name> --role ... [--module|--system] [--restart always|on-failure|never] [--max-restarts n] [--backoff-ms n]` persists a `DaemonSpec` to `.cortex/daemons.json` (the registry ARCHITECTURE §7 already specified) and generates an OS service unit under `<CORTEX_HOME>/units/`: a systemd `.service` on linux, a launchd `.plist` on darwin. Windows gets an `schtasks` command printed instead of a file. `install` deliberately does **not** enable the unit itself — that needs the operator's session / root and is OS-specific — but it prints the exact `systemctl --user enable --now` / `launchctl load` / `schtasks` command. `cortex daemon list` renders the registry; `cortex daemon uninstall <name>` removes the spec and best-effort deletes the unit.
  - **`cortex daemon run [name]` is a real long-lived supervisor**, not the short-lived CLI model: it boots a kernel, registers the daemon(s) through the **existing** `Kernel.registerDaemon` → init supervision machinery (`RestartPolicy` always / on-failure / never, exponential backoff, `maxRestarts` cap, sliding-window restart-storm detection — docs/PROCESS.md §9–§10), and stays alive until SIGTERM/SIGINT (or `--max-runtime-ms n`, for headless / test use). **No kernel code changed** — init already had the supervisor; this command is the thin CLI shell over it. This is also the piece that makes `attach`'s deferred interactive send-half possible.
  - **It is now the kernel's transport endpoint.** While `daemon run` is alive, the kernel serves a loopback control port and publishes its endpoint in `<CORTEX_HOME>/kernel.json` (host, port, OS pid, a per-kernel token, ABI version). Every remote action is answered by an existing kernel API through the dispatcher, so it is recorded in the kernel's `.crec` exactly like a local one — the transport adds reachability, not a side door (docs/ARCHITECTURE.md §12.1). `--port` pins the port instead of taking an ephemeral one.
  - **`cortex daemon stop` is now a command.** The server already answered `shutdown`; what was missing was a way to *ask* for it from the shell, so the only way to end a live daemon was to kill its OS process from outside. It now asks the daemon to stop through the same transport the other commands use, so the kernel shuts down cleanly (logs flushed, endpoint file removed) instead of being cut off. With no daemon running it says plainly that there is nothing to stop and exits non-zero.

- [x] **#040** `cortex audit` — surface tools that are untagged for reversibility (STATE.md §8.7) → implemented, and **sharpened by #025**: it now prints each tool's tag *and* distinguishes a declared tag from an inferred one. - [x] **#051** `cortex logs` — read back what a process *printed* → implemented (`--tail N`, `--follow`, `--timeout-ms N`). **The gap it closes:** the `.crec` log records what a process **did** — its syscalls, with arguments and results. It never recorded what a process **said**, because `console.log` is not a syscall, is not in the ABI, and never appeared in the log. So an agent's output went to the daemon's stdout — one anonymous stream shared by the daemon, `init` and every agent in the tree — and nowhere it could be read back from. With two agents running there was no way to tell which one printed what, and no way at all to ask an agent what it said after the fact. Now every process's printed output is captured to `processes/<pid>/output.log`, one stamped line per printed line, tagged `out` or `err`, and `cortex logs <pid>` reads it back from disk (so it works for a process that exited, and for one whose kernel is gone). **The mechanism is thin on purpose:** the kernel still does not know what a process said — it reports which process a body belongs to (`KernelOptions.agentScope`) and the CLI decides what "inside a scope" means: an `AsyncLocalStorage` holding the PID, which survives every `await` inside the body, so a line printed three seconds later by an agent parked on `recv()` still knows it is PID 7's. - [x] **#052** `cortex memory <pid>` — read back what a running process *knows* → implemented (`--region`, `--key`, `--prefix`, `--limit`). **The gap it closes:** the `.crec` log records what a process **did**, and for a `memory_write` the argument it records is a **hash**, not the value (ABI.md §4.4 — "full values would bloat the log"). - [x] **#054** `cortex wait <pid>` — wait for a process to end, and get its **real** exit code → implemented (`--timeout-ms N`). **The gap it closes:** the transport could show a process's state (`ps`), its output (`logs`) and its knowledge (`memory`), but nothing could **block** — there was no verb for "tell me when this finishes". - [x] **#055** The transport carries **streams**, not just commands → implemented (`cortex watch`; `Kernel.subscribe`; the `subscribe` command). **The gap it closes:** everything the transport had done so far was *request/response* — a client asked, the kernel answered, the client went away. So the kernel now reports facts as they happen (`Kernel.subscribe(listener)` → `process-start`, `process-exit`, `record`), and the transport pushes them on the same socket: a client sends `subscribe`, gets an ordinary acknowledgement, and then receives `{event: …}` frames. `cortex watch` is the shell's view — `cortex watch --pid 1234` prints the syscall frames in the same layout as `cortex trace`, plus the process-lifecycle lines, the moment they happen. **The interesting part is where the hook lives.** The obvious place is the dispatcher, and that would have been *wrong*: **seven** modules write records directly through `recorder.append()` — the dispatcher, the scheduler, the signal manager, the process table, `fork`, `init` and `checkpoint` — because four of them predate the dispatcher and own a record of their own. - [x] **#056** `cortex supervise <pid>` — the shell supervises a live agent → implemented (`--kill-after <ms>`, `--restart`, `--max-restarts <n>`, `--backoff-ms <ms>`, `--timeout-ms <ms>`). **The gap it closes:** a stream is only half a story. - [ ] **#057** A process that never wakes cannot be stopped gracefully → **open, and it wants a decision.** The signal queuing rule (PROCESS.md §7.2) says a signal aimed at a process that is not RUNNING waits in its pending queue until it transitions to RUNNING. But an agent parked in a `recv()` with no timeout, or one that never wakes at all, will never see the signal, so `SIGTERM` alone cannot stop it: the signal sits in the queue forever. `SIGKILL` is the only thing that works, and it is the difference between a graceful stop and a kill. **The options are a state-model question, so it needs a discussion before code:** (a) deliver `SIGTERM` immediately to a process that is BLOCKED *on a channel* (as opposed to one blocked on an LLM call or a tool), on the grounds that a channel wait is interruptible and an LLM call is not; (b) leave the rule alone and make every caller responsible for escalating to `SIGKILL` — which is what `cortex supervise` does today, and is honest but leaves a footgun in `cortex kill`; (c) add a "terminate now" variant of the kill path that skips the queue for `SIGTERM` specifically. `cortex supervise` works around it for now, and the workaround is documented where it matters.

- [x] **#067** `cortex wrap` reported success for a run that failed → **fixed.** A process that is **exiting** has not finished: the kernel records its exit code *after* it gets there — two disk writes sit between the two — so there is a real window in which the process table says "dying" and the code is still `null`. The wrapper used to read that window as "no code" and default it to `0`, so `cortex wrap -- <command that failed with 127>` sometimes reported **success**. The full smoke suite caught it twice in a row under load, and the failure looked exactly like the timeout bug fixed earlier: `process exited (code 0: completed)`. The lie was in two places, so the fix has two halves: the wrapper now **waits** for an ending it can trust — the zombie, which carries the code, or the reap, which leaves the exit record on disk (`attemptFinished`) — and the report never invents a zero for a code it did not see: a missing code is reported as unknown, not as success (`wrapOutcome`). Both are exported pure functions, so the rules are pinned on their own rather than left to a race; the end-to-end check now runs the missing command three times, because a race that only shows up under load is exactly the kind that survives a test suite and shows up in somebody's CI. 1 smoke check (675 → 676), reverse-verified twice: putting the missing code back to `0` → the check fails with "an exit code that was never seen must not be reported as success, got 0"; and counting `exiting` as finished again → the check fails with "a process that is exiting has not finished".
- [x] **#066** The dashboard's process table was a snapshot of the past → **fixed.** The dashboard is the operator's window, and its process list showed them a picture of the past: the table was re-read only when a process *started* or *ended*, so an agent that worked for a minute was shown as it was when it started — its state frozen, its spend frozen — while the page said "live connection" in the corner. **The kernel says what happens** (every syscall, every state transition, and when it happened), so the table is re-read when the kernel says something. The re-read is **throttled, not debounced**: a busy kernel says something every few milliseconds, and a re-read that waited for the silence would never happen — the table would sit frozen through exactly the busy period it exists for. That was not a theory: a real run against a real daemon measured **two tables in fifteen seconds** before the throttle and about **four a second** after it. **And the table now says what each agent was allowed to do** — the question `cortex ps` answers and the dashboard did not. The label travels with the row (`capsLabel`), produced by the same rule `cortex ps` prints (`formatCaps`, moved out of the command into `src/cli/process_view.ts` so the two views share it): `spawn` for a narrowed agent, `all` for one holding everything, `none` for one holding nothing, and `-` for a process whose capabilities were never recorded — which is *not* "everything", it is the absence of an answer. The page prints the label it is given and does not re-implement the rule, because a second rule is a rule that drifts. **And the footer says which way the page is being refreshed**: "live push (SSE), reconciled every 30 seconds" while the kernel is pushing, "polling every 3 seconds (the live connection is unavailable)" when it is not — it used to claim "auto-refresh · every 3 seconds" whatever it was doing, and in the live case it was not polling every 3 seconds at all. 3 smoke checks (672 → 675), all three reverse-verified: removing the re-read trigger → the table is never pushed again; giving the dashboard its own capability rule → the two views disagree (`pid 6 holds "none", got ` — the empty string a naive join produces); and putting the throttle back to a plain debounce → the table stops at two tables in four seconds.
- [ ] **#060** A process in a driver call is not parked, so the process table cannot show a stall in a model call → **open, and it wants a decision.** `BlockedReason` has `llm` and `tool` variants (and `budget` and `lock`), and the kernel never sets any of them: a process awaiting an `llm_call` stays RUNNING, because the cooperative scheduler does not preempt a running process (PROCESS.md §8.2). The consequence is that `cortex ps` calls a wedged agent `running`, and any host that reads only the process table will never see the stall. **The options are a state-model question, so they need a discussion before code:** (a) park the process in BLOCKED with `blockedOn = {kind:'llm', callId}` for the duration of the driver call, and wake it when the call returns — the honest state, but it changes when RUNNING → BLOCKED happens, and everything that reads the state (the scheduler's accounting of who is runnable, the wall-clock budget, the `ps` output) would have to be re-checked; (b) leave the states alone and make the *views* read the log — which is what `cortex top` used to do, at the cost of one log read per live process; (c) add a separate host-facing fact for "the call this process is in" — the kernel knows it, but `ProcessInfo` is frozen, so it would have to be a method (`Kernel.openCalls()`, which the ABI rules allow) rather than a field. **Option (c) has landed** (BACKLOG #068): the kernel keeps the pairing as it happens and the host asks it for the answer, so the view costs O(processes) instead of O(bytes). **What is still open is (a) vs (b)** — whether a process in a driver call should *be* BLOCKED. That is a state-model question, not a view question, and no view can answer it: `cortex top` can see that an agent is four minutes into an `llm_call`, but whether the process table should also say `blocked` is a decision about what RUNNING means. `cortex top` works today either way.
- [x] **#068** The host rebuilt what the kernel already knew → **fixed.** `cortex top` and `cortex supervise` both answer one question — *which call is this process inside, and for how long?* — and they used to answer it by reading the process's whole `.crec` and pairing the frames themselves. The kernel can answer it directly: it writes every syscall as an `enter` frame and its partner, and it knows which pairs are still open. The host was rebuilding a fact the kernel had, at O(bytes) instead of O(processes) — and the log of a long-lived agent grows for as long as the agent runs, so the operator's most frequent question got slower exactly as it was most needed. **The kernel answers now**: `Kernel.openCalls()` on the host side, `openCalls` on the transport — a read, like `ps` (watching is not doing, so it is not recorded). The entry is set when the `enter` frame is written and cleared when its partner is, and the `since` it reports is **that frame's own timestamp**, so the kernel's answer and the log's answer are the same number rather than two numbers that happen to be close. Measured against a live kernel with a 13 MB log: the log path took 273–283 ms per view, the kernel path 0–1 ms. **The call's arguments travel with it**, and that is not decoration: the arguments are what say a `wait` carries its own deadline, and a declared wait is not a stall — an earlier version of this dropped them, and the bounded `wait` was promptly called a stall, which the existing check caught, because the view and the supervisor must agree about what "stuck" means. **And the pairing is by call id, because a process can be inside two calls**: nothing forbids an agent from awaiting two syscalls at once, the second reaches the dispatcher before the first has parked the process (so both are admitted), and the second then traps because the process is no longer RUNNING — a bookkeeping that kept one slot per process would close the first call's slot when the second closed and report "nothing" for a process demonstrably still inside its `sleep`. A real run against a real kernel showed exactly that disagreement: the log said `sleep`, the kernel said nothing, and the process was still in the sleep. **A kernel that cannot be asked is not a kernel with nothing to say**: the reader returns nothing at all when the kernel is too old to know the command or is not answering, and the caller falls back to the log; an *empty* answer from a kernel that was asked means the kernel really has no open calls — and a process the kernel no longer holds is not reported at all, because a dead process's log keeps the `enter` frame of the call it was killed in and reading that as "still inside that call" is a lie. 5 smoke checks (676 → 681), all five reverse-verified: `cortex top` reading the log again → "cortex top still knows what a process is inside when the log says nothing" fails; the kernel stamping the time at query time instead of the frame's own → "the kernel and the log say the same thing about an open call" fails, and so does the stall marking, because a call that started "now" is never stale; the kernel dropping the arguments → both the declared-wait agreement and the bounded-wait view fail; the supervisor reading the log instead of asking → "cortex supervise finds the call even when the log says nothing" fails; and one slot per process instead of one per call → "a process with two calls in flight still reports the one it is inside" fails. No ABI change: a host method is not part of the agent surface, and `openCalls` is an additive transport command, so `KERNEL_ABI_VERSION` stays 1.0.0 and `KERNEL_PROTOCOL_VERSION` does not move either.

**Exit criteria:** the demo from `README.md` runs end-to-end on a laptop.

## Phase 4 — Killer demos

Three demos that prove the abstraction matters. Each one becomes a GIF in the README and a post on X / V2EX / HN.

**Order chosen for maximum signal:** lead with the demo that no existing tool can do, follow with the demos that show composability.

- [x] **#041** **Demo B (lead) — Pause across reboots.** A long-running inbox-watcher daemon checkpoints mid-thought, the laptop reboots, `cortex restore` brings it back exactly where it left off. This is the demo that makes people say *"oh, that's what's been missing."*
  - **Mechanism: working end-to-end via the CLI** (see `examples/checkpoint-agent.ts`). An agent calls `ctx.checkpoint({ tag, detach: true })` while running; the process SUSPENDS and a `.csnap` is written to disk. A *later, separate* `cortex restore --tag <t>` (or `--chain <id>`) re-materialises it as a new PID with its memory regions re-hydrated, and it continues. This required three fixes: a disk-backed `restoreContext` in `bootCliKernel` (the kernel default reads an in-memory map that is empty in a fresh invocation), seeding the PID counter from `maxPidOnDisk` (so restore does not reuse the suspended original's PID and collide on `.crec`/`.meta.json`), and resolving `--tag` from the `.crec` checkpoint record (the tag is not stored in the `.csnap`).
  - **Honest v0 caveat:** a checkpoint captures the *process image* — state, memory regions, budgets, lineage — **not the live JS call stack.** "Exactly where it left off" therefore means *memory is restored and the agent re-runs from the top, continuing past its own checkpoint marker.* The agent must make its progress idempotent via memory (the example gates phase 2 on a memory key). True continuation capture is a post-v0 concern.
  - **Polished (this pass):** the demo script is now a realistic inbox-watcher — it watches a fixed 6-ticket queue, classifies each ticket (`bug`/`feature`/`question`) via a stem regex, drafts a reply into the shared `semantic` region, and records the processed id in `episodic`; after 3 tickets it checkpoints + detaches; on `restore` it reads back the `done` set, skips the three already handled, and finishes the queue (`inbox cleared (6/6)`). The full spawn → reboot → restore run is captured in `examples/demo-b.capture.log`. **README visual:** `docs/demo-b.html` is a dependency-free animated replay; `docs/demo-b.gif` is produced by `examples/make-demo-b-gif.py` once Pillow is installed — the offline build sandbox blocks `pip install pillow`, so the GIF is generated on a connected machine, not in CI.
- [x] **#042** **Demo C — Fork and compare.** A coder agent reaches a decision point. We `fork` it, send the two branches different prompts, watch them diverge, then `cortex diff` to compare their final outputs and pick a winner. Extends to **agent search**: spawn N branches, evaluate, keep best.
  - **Mechanism: working end-to-end via the CLI** (see `examples/fork-compare-agent.ts`). Verified: `cortex spawn --role demo --module ./examples/fork-compare-agent.ts` → `[parent 2] forked as pid 3` → both branches run, each takes a different `llm_call`, each exits with its own reason → `cortex diff 2 3` reports *"diverged after 7 shared syscall(s) — fork recorded in pid 2 at byte offset 2307"* and lines up the two tails. Requires #038 (diff), which is done. The captured run lives in `examples/demo-c.capture.log` and replays in `docs/demo-c.html`.
  - **Honest v0 caveat (same contract as Demo B):** a forked child **re-runs its agent module from the top** with the parent's cognitive snapshot and memory regions; it does not resume at the fork point. The example distinguishes parent from child by writing a `forked` marker to memory *before* calling `ctx.fork()` — the child inherits it in its snapshot and skips the parent's block. Writing it after would not work: the child's snapshot is already sealed. That is a pattern the agent author applies, not a kernel feature.
  - **Polished (this pass):** the demo script is now a concrete decision — a coder commits to a fixed dedup requirement (high-volume event stream, memory-tight, tiny false-positive tolerated), forks, and the two branches each take a real, distinct strategy: branch A a counting Bloom filter, branch B an LRU-bounded hash set. Each branch writes a structured proposal object to the shared `semantic` region and prints it (concrete, diffable output instead of the old placeholder "state the problem in one sentence"). The full spawn → fork → `cortex diff 2 3` run is captured in `examples/demo-c.capture.log` and shows a real divergence (7 shared syscalls, fork at byte offset 2307, distinct A-only / B-only tails, separate final `llm_call` outputs). **README visual:** `docs/demo-c.html` is a dependency-free animated replay; `docs/demo-c.gif` is produced by `examples/make-demo-c-gif.py` once Pillow is installed — the offline build sandbox blocks `pip install pillow`, so the GIF is generated on a connected machine, not in CI.
- [x] **#043** **Demo A — Supervision tree.** A planner spawns three parallel coders, one hangs, planner detects timeout, kills it, spawns a replacement, gathers results. No glue code beyond the planner agent itself.
  - **Mechanism: working end-to-end via the CLI** (see `examples/supervision-tree.ts`). `cortex spawn --role planner --module ./examples/supervision-tree.ts` → planner spawns 3 coders (billing hangs on purpose) → *"billing (pid 8) missed its deadline — killing"* → respawns `billing#2` → gathers all three results from the shared `semantic` region → exits 0 with `planner complete: auth=ok(0),storage=ok(0),billing=respawned(0)`. The planner is ~40 lines of ordinary `async`/`await`; the restart policy is a `catch` block.
  - **This demo required the cooperative-continuation rework, which is now done.** The kernel used to run an agent body to completion inside the quantum that dispatched it, so a parent parked in `wait()` held its own tick forever and its children could never be dispatched — `wait()` deadlocked by construction, and the BACKLOG's "no glue code beyond the planner" bar was unreachable. `Kernel.#runQuantum` now *starts* the body and returns; the body lives in its own Promise across later ticks. Three pieces carry it: `wake_gate.ts` (defer a woken `wait()`/`recv()` until the process is back on the CPU, so the next syscall sees RUNNING instead of trapping ESTATE), `Scheduler.isLive` (a live body ⇒ report `parked`, leave RUNNING, never re-queue), and `Kernel.settle()` (run to quiescence, since one tick is no longer one agent). Docs updated: PROCESS.md §8.2, ABI.md §4.1.
  - **Two real bugs fell out of it, both fixed with regression tests:**
    - *Scheduler run-queue desync.* `#selectNext` dropped stale nodes from the queue array but left the PID in the `#queued` membership mirror, so `enqueue()` — idempotent by checking that mirror — became a permanent no-op and the process sat READY forever, dispatched by nobody. Nothing in the old run-to-completion model could reach that state; a woken body that blocks again on a later `wait()` can.
    - *A late `wait()` lost the child's status.* init auto-reaps zombies, so a supervisor waiting for child A and then child B found B already gone: `wait(B)` trapped `ESRCH` (or parked forever). `ProcessTable` now retains each reaped child's `WaitResult` for its parent (`takeReapedChild`/`takeReapedChildAny`), consumed once like a real reap.
  - **New syscall surface:** `wait(pid, { timeoutMs })` traps `ETIMEDOUT` on a deadline (`timeoutMs: 0` polls without parking). A timeout does *not* kill the child — that stays the supervisor's decision, which is what makes the restart policy expressible in the agent rather than in an orchestrator.
  - **Polished (this pass):** the planner/coder script now does a real task — each coder generates one section of a README for a fictional library ("tinylog") and the planner assembles the finished doc from the shared `semantic` region (captured run in `examples/demo-a.capture.log`). **README visual:** `docs/demo-a.html` is a dependency-free animated replay; `docs/demo-a.gif` is produced by `examples/make-demo-a-gif.py` once Pillow is installed — the offline build sandbox blocks `pip install pillow`, so the GIF is generated on a connected machine, not in CI.

**Exit criteria:** all three demos can be reproduced by a stranger following the README in under 10 minutes.

**Next release:** `1.1` — additive work only. The self-recorded-syscall
cleanup (see the `1.0.0` entry above) is **done**: all seven syscalls now
record through the dispatcher, and `SELF_RECORDED_SYSCALLS` is empty. The
live-kernel transport (ARCHITECTURE §12.1) has landed too, which makes
`cortex send` / `cortex kill` / `cortex attach --interactive` act on a
*running* kernel instead of on the files it left behind. The transport now
also reaches the snapshot: `cortex checkpoint <pid>` takes a snapshot of a
running agent (it could never succeed before — a checkpoint captures a live
process, and the short-lived CLI kernel holds only init), and `SIGUSR2`
means "checkpoint now" for real, which is the only way to ask *another*
process to snapshot itself (`checkpoint` is a self-syscall; the ABI gives it
no target argument). The transport now also owns the *lifecycle*: `cortex spawn
--live` creates an agent **inside** the running kernel (the default `spawn`
still boots its own — one kernel per invocation — so the PID claim keeps the
two off each other's logs), `cortex daemon stop` asks a running daemon to shut
down cleanly instead of having its OS process killed from outside, and
`cortex restore --live` puts a snapshot *back* into that kernel, so a restored
agent keeps working instead of living and dying with the command that restored
it. And a snapshot now outlives the kernel that took it: the agent's spec is
persisted when the process is *created* (`processes/<pid>/spec.json`), not
only when it exits, so "pause, reboot, come back" works for an agent that was
still running when its kernel died. And a live agent's *output* and its
*memory* are now addressable: every process's printed lines are captured to
`processes/<pid>/output.log` and read back with `cortex logs <pid>`, and
`cortex memory <pid>` reads a live process's memory regions — which is the
half of "why did the agent do that?" the syscall log cannot answer, since it
stores a hash of a memory value rather than the value. (Reading memory also
surfaced a real bug: a daemon-registered agent never had its declared regions
*bound*, so it died on its first `memory_read` with ENOENT — see #053.) And a
process's **ending** is now addressable too: `cortex wait <pid>` blocks until a
process finishes and reports the real exit code, and the kernel grew the
host-facing primitive behind it (`Kernel.awaitExit`) because a host is not in
the process tree and therefore cannot use the parent-child `wait` syscall at
all — see #054, and docs/HACKING.md §7 for the whole "writing a host" story.
What
remains for `1.1` comes out of the
Icebox below. The transport now carries streams as well as commands: the kernel
reports what it does as it does it (`Kernel.subscribe`), and the transport
pushes those events to a client that asked for them — `cortex watch` is the
shell's view of it (see #055).

## Icebox (post-v0.1)

Things we want, but not yet:

**From the v0 design:**
- ~~Capability / permission system (was Phase 1, demoted)~~ → **shipped in `1.0.0`** as `acquire` / `release` / `caps` over six capabilities (ABI §4.9). Demoting it in v0 was right — nobody had a workload that needed it yet — and §9.2's "v1 may introduce it" is now closed.
- Sandbox fork (STATE.md §3.2) — copy-on-write filesystem overlay
- Shadow process (STATE.md §3.4) — same state, different driver config
- Two-phase tool pattern (`stage` / `commit`) for irreversible actions
- `cortex doctor` to probe driver fork-safety claims
- CRDT-backed shared memory regions (if last-write-wins hurts)

**From the long-term vision:**
- Distributed cortex (multi-host process tree)
- WebAssembly driver sandbox
- GUI process inspector (think `htop` for agents)
- Time-travel debugger UI on top of `.crec` files
- Capability marketplace (signed, versioned skill packages)
- Erlang-style hot code reloading for running agents
- Plan 9-style "everything is a file" — expose every syscall as a file in a virtual filesystem (`/proc/<pid>/llm_call` you can `echo` into)
- Formal model of the syscall ABI in TLA+ or Alloy
- Optional Temporal-backed persistence driver (prove our "you can build cortex on Temporal" claim)

**From the live-kernel transport:**
- A **queued** signal loses its sender: the pending queue holds the signal
  only (`pendingSignals` is part of `ProcessInfo`, and the ABI is frozen), so
  a `SIGUSR2` that had to wait for its target to run again is recorded
  without a `from`. Preserving the sender needs a `ProcessInfo` change —
  a `2.0` conversation, not a `1.1` one.

## Conventions

- One issue per checkbox above. When you start work, comment on the issue with `[wip]`.
- Commits reference issues: `kernel: implement scheduler (#013)`.
- Anything that changes the ABI or the state model requires a MANIFESTO-level discussion in an issue first.
- We do not close issues for being "stale." Stale means we have not decided. Decisions get made, not aged out.
- External critique is welcome and gets logged. See [`docs/CRITIQUE.md`](./docs/CRITIQUE.md) for the running record of what reviewers said and what we changed because of it.
